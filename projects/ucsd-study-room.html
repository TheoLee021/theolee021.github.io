Case Study

ucsd-study-room

Book a UCSD study room by just asking your AI assistant.

Role
Solo developer
Timeline
Mar 2026 – present
Stack
Python · Playwright · MCP · PyPI
GitHub PyPI Claude Code plugin

TL;DR

Problem
Booking a Price Center study room means finding a hard-to-find site called T-RES, then clicking through about ten steps.
Solution
A Python tool that drives the booking site with a real browser, exposed as a CLI, an MCP server and a Claude Code plugin.
Result
One sentence to book. Search, book, list and cancel work from the terminal or any MCP client, published on PyPI.

Why I built this

I spend a lot of time in the Price Center study rooms, and people walking by kept stopping to ask me the same thing: how do you book one of these?

The honest answer was not short. The rooms are booked through a site called T-RES, and searching “ucsd study room” rarely gets you there. You have to dig. Once you find it, this is the path:

  1. Log in with UCSD SSO and approve Duo
  2. Click Book Now
  3. Pick a date and a time range
  4. Click Search
  5. Choose an available room
  6. Enter the number of attendees and click Add Room
  7. Click Next Step
  8. Type your full name twice, then your email
  9. Accept the terms
  10. Click Create Reservation

What I wanted instead: “Book a study room tomorrow from 2 to 4pm.”

Architecture at a glance

All of the logic lives in one core package. auth handles SSO and the saved session, booking drives the T-RES pages, config stores your name and email, and updater checks PyPI for new releases. The CLI and the MCP server only translate input and output. The Claude Code plugin contains no Python at all: it is a skill plus an .mcp.json that starts the MCP server with uvx.

Keeping the interfaces thin pays off with every feature. Cancellation, for example, was written once in booking.py and wired into both the CLI and the MCP server in the same change.

Key decisions

1. No API, so drive a real browser

Context
T-RES has no public API, and every request sits behind UCSD’s SAML single sign-on plus a Duo Push second factor.
Options
Reverse-engineer the HTTP requests and replay them, or drive a real browser the way a person would.
Decision
Drive real Chrome with Playwright. Login happens once in a visible window so the user can approve Duo. The resulting storage state (cookies plus local and session storage) is saved and reused by headless Chrome for every search and booking.
Trade-off
Every command launches a browser, so it is slower than a raw HTTP call, and a T-RES redesign can break selectors. In exchange I never replicate the SAML redirects or the Duo flow, and the tool behaves exactly like a logged-in student.

Credentials go into the OS keyring (macOS Keychain, Windows Credential Locker, Linux Secret Service), never a plain file. A saved session is trusted for seven days. If the site bounces a request back to SSO sooner, the tool opens Chrome, fills in the stored credentials, waits for Duo, and retries the same request instead of failing.

2. One core, many interfaces

Context
The first release was a CLI and an MCP server whose tool descriptions and responses were written in Korean, with setup docs aimed at Claude Code.
Decision
Two days later I made the MCP server client-agnostic: English descriptions and responses, a study-room-mcp entry point that uvx can run without a manual install, and setup docs that work for Codex CLI, Gemini CLI and Cursor too.
Result
The same five tools (search_rooms, book_room, my_events, cancel_reservation, login) work in any MCP client, and the CLI exposes the same core through seven commands. The architecture diagram above shows the split.

3. Shipping to two worlds

Context
People install this either as a Python tool or as a Claude Code plugin. Both should stay current without the user doing anything.
Decision
Split the project into three repositories by what changes. ucsd-study-room holds the Python code and ships to PyPI. ucsd-study-room-plugin holds the skill and .mcp.json. claude-plugins is the marketplace that lists the plugin and its version. The plugin’s .mcp.json runs uvx --refresh, so every MCP start resolves the newest release from PyPI.
Result
A Python change needs only a PyPI release. A skill or config change needs a plugin push plus a marketplace version bump. CLI users get a once-a-day update notice and a study-room update command.

Gotchas I hit

  • A plugin only loads when the repository root is the plugin root. I first kept it in a plugin/ folder inside the main repo, and Claude Code could not find the skill.
  • Claude Code caches plugins by marketplace version. Pushing to the plugin repo changes nothing for users until the version in marketplace.json goes up.
  • The marketplace source type is "url" with a full .git URL, not "github".

In use

Right now a friend uses it regularly to book rooms. It is a small audience, and I would rather say so than round it up.

What's next

I still think of this project as unfinished. These are the next steps, in the order I would take them.

  1. See every open room at a glance

    Today you have to name a time before you see anything. A day view of open slots matches how people actually decide: find a gap, then book it.

  2. A gentler login

    Login still opens a Chrome window and waits for Duo. That is the price of driving a real browser, and it is the biggest hurdle for a first-time user.

  3. Cover more than Price Center

    Other study spaces at UCSD are booked on different platforms. Bringing them behind the same core is the step toward one place to book any room on campus.

  4. A web app for everyone at UCSD

    Not everyone uses a terminal or an AI assistant. A web front end would be a fourth interface on the same core, and the core-first structure is what makes that feasible.
